## 技术选型结论：x86-64 主机跑 arm64 模拟器（用户提问）
- 可行性：AVD arm64-v8a 镜像可在 x86 主机装，但纯 QEMU 软件模拟（冷启 ~11.7s、native so 加载成功率 ~82%、慢 5-10x）。

- 建议：非 root 单变量验证可用 x86_64 Google Play 镜像；稳定出数据仍需非 root 量产真机或云真机平台（Testin/WeTest/MQC）。

## 追加：gadget 路线的最终结论（决定性死结 + UI 搜索成功证据）
- **App UI 免登录搜索在这台 FP4 + 重打包 APK 上真实出数据**：deeplink `taobao://s.taobao.com/search?q=iphone17` → 截图 `screenshots/uistatus/screen.png` 显示 iPhone17 商品列表（¥5999/¥5299，天猫店铺），游客态无登录无风控页。**证明免登录搜索目标本身可达，服务端允许**。
- **gadget 进程内模式的实现限制（重要）**：任何对淘宝业务方法的 `implementation` 替换（buildParams / n9f.r，即使只做值拷贝、不保存 Java 对象引用）都会导致 App SIGABRT：`JNI DETECTED ERROR ... jobject is an invalid JNI transition frame reference ... in call to IsInstanceOf from tb.n9f.r / InnerProtocolParamBuilderImpl.buildParams`，线程 Orange_Listener。这是 frida-java-bridge 17.16.4 在 gadget 进程内 + Android 15 上无法可靠 implementation-replace 高频方法。**gadget 模式只能用 Java.use 主动调用，不能 hook**。已建多个专用 bundle：`rpc_native_only_bundle.js`（纯 nativeSearch，稳定）、`rpc_native_diag_bundle.js`（probe+nativeSearch，稳定）、`rpc_main_thread_bundle.js`（主线程版，稳定）、`rpc_capture_safe_bundle.js`/`rpc_n9f_capture_bundle.js`（hook 版，会崩，勿用）。
- **决定性死结：重打包破坏 SecurityGuard 签名**。nativeSearch 稳定执行但全部返回 `ANDROID_SYS_GENERATE_MTOP_SIGN_ERROR` / `mappingCode EC40002`。logcat：`[getUnifiedSign] get sign failed and SecException errorCode 1927, appKeyIndex=0, authCode=null` at `tb.n9f.r` → `getSecurityFactors`。阿里云官方文档 19xx 系列错误码（1902=安全图片与 APK 签名不一致）指向：**gadget 需重打包→自签名→SecurityGuard 安全图片(yw_1222)与 APK 签名不匹配→无法生成 x-sign/x-mini-wua**。已排除：data 格式（完整 764 字符结构也失败）、线程（主线程 post 也失败）、Mtop 实例（INNER cfg.utdid 唯一非空，选择正确）、authCode 时序（UI 搜索后仍失败）。
- **结论**：gadget 静态注入能连上、能主动调用，但拿不到真实签名，无法用于发有效搜索请求。真正可行路线需换思路：① 不重打包的 root 设备（frida-server attach，签名完整）；② 云真机平台（非 root 量产机 + 已 root 的调试机各一台）；③ 接受 UI 自动化搜索 + 抓包/读结果（非 API）。 Hermes: bridge 已支持 `FRIDA_BUNDLE` 环境变量选 bundle，`/api/search/native-main` 主线程路由，`tools/frida_rpc_bridge.py`。

## 追加：arm64 模拟器安装淘宝的最终结论（PackageInstaller 死锁，本地路线彻底堵死）
- **audio HAL 死亡循环定位并解决**：`android.hardware.audio@2.0-impl.so` + `android.hardware.soundtrigger@2.0-impl.so` 在 arm64 软件模拟下崩溃，AudioService 每 0.5s "Audioserver died" + `Waiting for service media.sound_trigger_hw`。`/vendor` 可 `mount -o rw,remount /vendor`，把两个 so 改名（a2.bak/st.bak）后循环停止。但**重启后 so 会恢复**（`-no-snapshot-load` + vendor overlay 未持久化），需每次启动后重做。
- **决定性死锁点（与 audio/dexopt/空间无关）**：即使 audio 循环停止、data 扩到 3.8G、pm.dexopt 全 skip，pm install 仍在 `PackageInstallerSession.write()` → `AssetManager.openXmlAssetNative()` 反复锁竞争（Long monitor contention）死锁，7 分钟 timeout（EXIT=124）。install session 状态 `sealed=true`、135M 数据（base.apk 95M + 63 个 arm64 so）完整解压到 `/data/app/vmdl*.tmp`，**卡在最后写 packages.xml 的 native XML 序列化**。日志证据：`E Pm: at IPackageInstaller$Stub$Proxy.openSession`、`Long monitor contention ... PackageInstallerSession.write() at AssetManager.openXmlAssetNative() for 1.6s`。这是 arm64 QEMU TCG 下 ART native XML 操作的死锁 bug。
- `pm install-commit <sessionId>` 手动提交报 `SecurityException: Caller has no access to session`（session 属 shell UID，root 无法跨 UID commit）。
- **结论：本地 arm64 软件模拟器无法安装淘宝 91MB APK，签名排查所需的"正版 APK 可运行宿主"在本地不可得**。已尝试并全部失败：新版 emulator 不支持 arm64 全系统模拟、x86_64+berberis 翻译 so 崩溃、非 root 真机 frida ptrace 被 SELinux 拒、gadget 重打包破坏签名(1927)、arm64 模拟器无法装 APK。剩余路线：ARM 云真机（唯一同时满足"官方 APK 完整签名 + root/frida 可 attach + 真 ARM 无翻译"），或手动组装已安装目录（高风险复杂），或接受真机 UI 自动化搜索（已实证可出数据）。
- 模拟器当前状态：AVD `taobao_arm64_api27` 运行中，root 可用，frida-server 17.16.4 在 27042，frida attach 可用（58 进程），但淘宝未安装。启动命令见上条。

## 追加：手动组装 /data/app + packages.xml 排查（用户选，进行中）
- 用户选"手动组装已安装目录"绕过 PackageInstaller 死锁。方法：PC 端 Python zipfile 解压官方 APK → `taobao_appdir/com.taobao.taobao-xem8TFzHo0Q/`（base.apk 95M + lib/arm64/ 63 个 so，共 141M），adb push 到 `/data/app/`，chmod 755/644，SELinux context 自动为 `apk_data_file:s0`（正确）。
- 手工在 packages.xml 插入 `<package name="com.taobao.taobao" codePath="/data/app/com.taobao.taobao-xem8TFzHo0Q" nativeLibraryPath=".../lib/arm64" primaryCpuAbi="arm64-v8a" version="866" userId="10120"><sigs count="1"><cert index="100" key="<淘宝证书DER hex>"/></sigs></package>`。证书 DER：从 `META-INF/CERT.RSA`(PKCS7) 用 openssl 提取 PEM→DER，583 字节，SHA-256 `c5e9bc4c...`，CN=taobao。
- **坑1（致命）：Python `open(...,'w')` 在 Windows 把 LF 写成 CRLF**，导致 PMS `Settings.readLPw()` 解析 packages.xml 失败 → `NullPointerException: VersionInfo.fingerprint on null` at PMS.java:2571 → system_server 崩溃循环 + RescueParty level 2 清空 packages.xml。修复：用 `open(...,'wb')` + `write(new.encode())` 保持纯 LF（CR count 必须为 0）。
- **坑2：RescueParty**。一旦 system_server 连续崩溃，`sys.rescue_level=2`、`/data/system/uiderrors.txt` 存在，每次启动 RESET 清空 packages.xml。恢复需 `rm -f /data/system/uiderrors.txt` + push 正确 packages.xml + 冷启动；反复失败后需 `-wipe-data` 彻底重置。
- **坑3：cert index 冲突**。index=18（系统 app 已用）→ PMS 崩溃；index=100（独立）→ 系统正常但 PMS 启动后**从 packages.xml 删除淘宝条目**。
- **当前卡点（未解）**：系统正常启动（94 包，0 FATAL），app 目录存在，PMS 日志：`Parse times for .../base.apk: parse=1460ms` → `collecting certs` → `Failed to scan .../com.taobao.taobao-xem8TFzHo0Q: Application package com.taobao.taobao not found; ignoring`（PMS.java:11448，SCAN_REQUIRE_KNOWN 分支 `mSettings.getPackageLPr(pkg.packageName)==null`）。即：我写入的 package 条目在 scanDirLI 之前就被 PMS 从 mSettings 移除了。推测是 PMS 读 packages.xml 后 collectCertificates 校验签名与目录 base.apk 不一致（可能 v1/v2 签名方案差异）导致 prune。下一步：用 frida hook system_server 的 `Settings.getPackageLPr` / `PackageManagerService.collectCertificatesLI` 精确诊断，或改走 frida 运行时调用 PMS 安装 API。
